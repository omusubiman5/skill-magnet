## 確定した問題と今回の修正範囲

1. 旧実機テストはメニューのrootをUIA `InvokePattern.Invoke()`で呼んでおり、物理クリックの証明になっていなかった。基準commitではrootの物理クリックへ変更した。
2. nativeの空command分岐が入口ログ前に終了していた。基準commitでは観測可能なエラーへ変更した。
3. 診断ログの同期書き込みと共有ファイルが競合・遅延要因になり得た。基準commitでは実行単位の非同期writerへ変更した。
4. 実機テストの終了処理と同時期にTkクラッシュが観測された。Close処理を修正し反復成功と報告されたが、時間的一致だけで元の根本原因が確定したとは扱わない。

レビューはこの4点と再起動への影響に絞る。新しい重大な欠陥を発見した場合だけ範囲を広げ、その証拠を残す。

## 実行手順

### 1. 現状確認と差分レビュー

status、HEAD、導入版、既存ログを短い出力で確認する。基準commitの差分を読み、物理クリック、終了時のworker／callback／lease、診断writerの終了処理が成立しているか確認する。ソース文字列の一致テストだけで動作確認済みにしない。

既存の407件を理由なく再実行しない。ログの所在が不明なら、関連する出力先に絞って一度検索し、不足を明記する。同じ検索を繰り返さない。

### 2. ビルドと導入

既存のビルド手順・CLIを読み、実際の引数を確認して使う。候補は`pyproject.toml`、`.github/workflows/test.yml`、`native/windows-modern-context-menu/build.ps1`、`build-package.ps1`。未確認のコマンド名を創作しない。

基準コードをビルドし、導入対象とversion・コード識別子・payload digestを照合する。独立2ビルドが既存リリース要件なら一度だけ行う。MSIX署名や証明書時刻が変わる場合、ファイル全体のバイト一致を勝手に要求せず、既存の論理payload比較方式に従う。

ユーザーは本修正の導入・push・mergeを既に承認している。通常の再導入について同じ承認を取り直さない。既存の設定・library・transactionとruntime skill領域を保全する。

### 3. Explorerの実機確認

`tests/powershell/windows-explorer-direct-root-field-test.ps1`の実際の処理と引数を読む。現在の引数は`Config`、`InvokeEvidence`、`FieldBundle`。構成ファイルは内容を確認して選び、成果は新規の専用出力先へ保存する。

導入済み候補で正式シナリオを一巡する。「一回」は必要シナリオ一式の実行であり、クリック一回だけで全面合格にする意味ではない。

- 選択フォルダー／背景からの実際の右クリック経路で、対象と処理が一致する。
- Skill Magnet rootを物理クリックし、nativeの起動記録と表示された画面を照合できる。
- 処理中表示、二重投入、通常Closeと再起動の必要ケースが成立する。直前の同一コードの有効な反復結果は再利用する。
- 元から存在するskillフォルダーを登録元として読むことと、その場所へのインストールを混同しない。
- 失敗時に原因と次の操作が分かり、保存済み状態から再開できる。

失敗したら、そのrunのログ・PID・時刻・段階を保存し、仮説、証拠、修正箇所を短く記録する。失敗箇所を修正して関連ケースを再実行する。テスト側のcleanupによる障害と製品側の障害を区別する。強制killを通常Close成功として数えない。

### 4. 証跡・ドキュメント・最終テスト

実機成功後に限り、現在のスキーマに従って次を更新する。

- `docs/evidence/windows-explorer-direct-root-0.5.9.log`
- `docs/evidence/windows-explorer-direct-root-0.5.9.json`
- `docs/windows-explorer-leaf-launch-results.md`

台帳の旧version、旧件数、旧メニュー説明を今回の観測値へ訂正する。期待値をコピーしてPASSを作らない。release code、導入payload、実機ログの対応を残す。既存の原因調査・対応報告へ今回の結果を追記し、同じ内容の報告書を増殖させない。

証跡更新後、`python -m unittest discover -s tests -v`を一度実行し、ledgerを含めた結果を取得する。新規修正がなければ同じ全件テストを繰り返さない。長いコマンドは終了コードと出力を確実に回収できるログへ保存し、出力紛失を理由に再実行しない。skipは理由つきで別記する。

### 5. push・CI・merge・同期

変更対象だけをcommitし、この指示書も引継ぎ資料として含める。既存PRがあれば更新し、なければPRを作る。CI結果と必要なmerge条件を確認し、成功時にmergeする。保護ルールを迂回しない。

本体の通常checkoutとスキル保管庫は、現在のdirty状態・ahead/behind・remoteを確認して同期する。fast-forward可能ならその方法を使う。本体には過去にmainが追加／取消commitの組でaheadだったとの情報があるため、現在の差分を確認してから履歴を保全して処理する。hard resetやユーザー変更の破棄は禁止。

## 作業量の制御

- 既存の成功結果はコード・環境・対象範囲が一致する場合に再利用する。
- 全スキル再取得、全リポジトリ再調査、無関係な監査、理由のない追加テストは禁止。
- 一つのログは必要箇所だけ表示する。長時間処理は完了通知または間隔を空けたpollで回収する。
- サブエージェントは必須ではない。利用枠エラーが既に発生しているので、同じ失敗を繰り返して起動しない。
- 追加API・追加購入・usage resetを要求または実行しない。
- 先行回答の2,000〜4,000トークンは未検証の見積り。8,000上限も撤回済み。保証された予算や完了見込みとして扱わない。
- 進捗は確認できた新事実だけ短く伝える。失敗で追加作業が必要になった場合は原因と範囲を伝えて続行する。
