# 「左の状態」― 継ぎ足し構造の原因調査

調査日: 2026-09-09。対象: Skill Magnet、作業開始時HEAD `6190f5a6ff6876215a9624cf1a2a9c8be046d68e`と未コミット差分。依頼の「左の状態」は例外メッセージではなく、局所修正の蓄積によって全体の整合・保守性が失われているという指摘として調査した。

## 結論

問題は確認できた。機能を足したこと自体より、旧経路を残したまま別経路を追加し、要件と矛盾する実装へテストの期待値を合わせ、さらにソースと導入物が別の組合せになっていたことが原因である。個別テストの成功を製品全体の設計整合の証拠として扱った主担当の検証方法にも不足があった。

## 観測した事実

## 修正の設計

1. OS adapterは対象folderを渡して共通画面を開く。pack/skill一覧とcommitの決定は現行設定を読むPython側に一本化する。FR-15/22に適合していた既存実装を基準に回復し、通常更新時の再登録を足して辻褄を合わせない。
2. Library UIは入力、非同期実行の起動、結果表示を担当する。使われない同期版6経路を削除し、送信・検証・有効化の実処理はLibraryTransactionを使う。
3. transactionの状態と、送信済みの可能性・破棄可否はGUIに依存しない共通の判定へ集約する。UIと実処理が同じ判定を使用する。
4. 原因例外をたどるOS障害判定を共通化し、実際のConfig.loadを通す回帰試験で保証する。
5. GitHubを唯一の正本とし、一時領域の消失時再作成・未送信編集の消失通知は保持する。利用者の既存登録元を削除しない。
6. 最終ソース一式からwheelを作る。wheel、導入Python、native source、メニュー契約を同じ候補へ結び付ける。過去のCIや別候補のPASSは今回の証拠に流用しない。

## 受入基準

単一rootから管理・登録・実行の選択肢が実際に見えること、設定更新後もOS再登録なしで現行設定を参照すること、背景folderと即時起動失敗のnative契約、ラップされた権限例外、状態別の破棄判断、一時領域消失の復旧を検証する。配布物と導入物の一致も確認し、実施していない外部サービス操作や実Explorer操作を成功扱いしない。

## リリース記録の不一致と是正

途中の全件試験で残った1件は、旧候補の419件・commit・wheel・実機証拠を現在の437件へ照合していたためである。これは単に試験件数を更新すればよい問題ではなく、記録の参照先が異なる候補を指す状態だった。

ソースをcommitへ固定し、そのソースと導入版の一致を確認したうえで実Explorer証跡を新規採取した。旧記録と証跡は履歴へ保存し、現在の集約記録を同一候補へ更新した。テストとrelease gateの条件を変更せず、最終全件試験とWindows MVPゲートが成功した。詳細は[対応報告](fix-report-structural-drift-2026-09-09.md)に記録した。

## CIで判明した証明書rollbackの不整合

全件試験と証跡gateを通過した後、実MSIXの更新・復旧試験が失敗した。現在版を片付ける処理が、復旧先の旧版と共有する署名証明書まで削除していた。backupには所有情報はあっても削除した秘密鍵を復元する機能はなく、旧版の再登録時にCurrentUser/Myの証明書が欠落した。

復旧前に両状態の証明書identityを検証・比較し、共有する証明書を残すようにした。置換証明書のcleanupと所有権検証は保持した。修正前に失敗する回帰を追加し、修正後は関連6件と導入版3件で成功した。最新のsource・wheel・field証拠は、この修正を含む候補へ更新している。
