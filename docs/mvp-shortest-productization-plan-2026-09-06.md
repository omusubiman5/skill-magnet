# Skill Magnet：MVPで最短に製品化する実行方針

作成日：2026-09-06

## 1. 到達点

**右クリックで開く。作ったスキルを登録できる。登録したスキルを選び、依頼と一緒にデスクトップアプリへ渡せる。失敗しても画面から復旧できる。**

この利用経路を通すことをMVPの目的にする。テスト収集器の高機能化、証跡形式の拡張、内部構造の作り直しを目的にしない。

本書は製品化の指示書であり、実装・公開の完了報告ではない。今回の依頼では本書だけを作成する。

## 2. 最初の出荷範囲

最短の出荷案は **Windows版MVP** とする。Codex Desktopアプリ／Claude Codeデスクトップアプリへの既存連携を維持し、各経路を確認する。Library Managerの登録・更新・削除は利用者が既に求めた中核機能なので残す。

macOS対応は削除せず、Windows版MVPの出荷判定から分離する。macOSの完成とは表示しない。現在の `policy/product-policy.json` は両OSの確認を製品完成の条件にしているため、実装時にはWindows限定の出荷区分を明記し、README・出荷条件・判定処理を同時に整合させる。既存の総合gateを通ったことに書き換えてはいけない。

## 3. 残す機能と利用者の操作

| 場面 | 利用者の操作 | アプリが行うこと |
|---|---|---|
| 起動 | フォルダーまたは背景を右クリックし、Skill Magnetを押す | 選択フォルダーを保持して画面を表示する |
| スキルを使う | パック・実行先・依頼を入力して実行 | GitHub固定commitと内容を検証し、新しいデスクトップタスクへ渡す |
| 登録 | 作成済みスキルのフォルダーで「このフォルダーのスキルを登録」 | 単一スキル・パック・複数パックの親を判定する。再選択を要求しない |
| 管理 | 一覧の対象を選び更新または削除 | 対象を示して確認し、その変更をGitHubへ公開・マージ・反映する |
| 復旧 | エラー画面の再試行、または閉じて再起動 | 保存済みの処理から再開し、重複登録・重複PRを防ぐ |

一覧では「スキル」「パック」を区別する。登録結果を選択・表示し、CMA004などの登録先がすぐ分かるようにする。

GitHub URLは既存値を表示する。初回未設定時だけ入力を求める。Draft directory、repository名、skill ID、pack ID、transaction ID、OSの手入力は要求しない。INDEXがないことだけで登録を拒否しない。特定の英語見出しだけを登録要件にしない。

## 4. 今回増やさないもの

- 7段階のタブ、送信・マージ確認・反映を別々に押す操作。
- 新しい管理機能、見た目の全面改修、汎用フレームワーク。
- UIテスト収集器の一般化、追加の証跡レイヤー、独自の全操作自動化基盤。
- AI回答の品質を監視して「依頼完了」を保証する仕組み。製品が確認するのは依頼の受け渡しまで。
- macOSの追加実装・実機対応をWindows版の修正と同時進行すること。

既存コードや利用者データを一括削除して縮小しない。対象外機能の拡張を止め、今回通す経路への変更だけに限定する。

## 5. 起動と復旧の最小仕様

1. 起動受付後、ネットワーク通信や保管庫検査を待たず画面と処理中表示を出す。
2. 二重起動は既存画面へ案内する。連続クリックで登録処理を増やさない。
3. 通信・外部コマンドには有限のタイムアウトを設ける。失敗時は対象と失敗操作、再試行方法を画面に表示する。
4. 「閉じる」は処理中でも応答する。再起動すると保存状態を読み、送信済みか照合して続行する。
5. マージ待ちは待機表示にする。ユーザー操作が必要な場合は該当PRへのリンクと具体的な操作を示す。
6. 復旧にはソース編集、内部ID入力、手作業でのlock削除を要求しない。外部障害が続く場合も閉じる・後で再開する・診断情報を取得する操作を提供する。

SKILL.mdを `.codex/skills`、`.agents/skills`、`.claude/skills` にインストールしない。登録元・作業対象・一時編集場所を分ける。元スキルと利用者の既存ファイルは保護する。

直前のWORKER報告では、正式fieldはクリックとnative invokeを通過した後、Library Managerの画面準備通知を待つ段階で停止している。これは引継ぎ情報であり、本書作成時に再現確認した事実ではない。画面そのものが出ていないのか、表示済みでも通知だけが出ていないのかは切り分けが必要。

**最初の作業は、この1件を直接起動とExplorer起動で比較すること。** 計測の12秒超過だけで製品が壊れていると断定せず、画面の応答、処理の進行、終了と再起動を確認する。

## 7. 実行順序

1. 管理担当が最新差分と上記停止ログを読み、失敗操作を1つ特定する。既存の成功済み調査をやり直さない。
2. Terra 1名に、その再現と最小修正だけを渡す。対象関数・期待動作・確認方法を指定する。根因不明の製品化全体を丸投げしない。
3. 修正箇所に必要な回帰確認を行う。動いたら候補を固定して1つの配布物を作り、同じ配布物を導入する。
4. 下記のMVP受入操作を実際のExplorerと画面で確認する。収集器だけの不具合なら、実操作・画面・アプリログで同じ条件を確認する。自動試験の失敗記録は残し、手動結果とは区別する。
5. 確定したWindows版MVPの出荷条件と文書を整え、必要な全体テスト・CIを実行する。製品の不具合は修正し、対象外判定は出荷範囲変更として明記する。
6. 成功した候補をcommit・push・CI確認・mergeし、通常checkoutと導入版の対応を確認する。最後に配布物・結果・残る対応範囲だけ報告する。

失敗したら、同じ操作を根拠なく再実行しない。製品の失敗か試験手段の失敗かを確認し、修正した仮説だけ再検証する。再buildは配布内容を変更した場合に限る。

## 8. MVPの受入条件

| 必須操作 | 合格条件 |
|---|---|
| 選択フォルダー／背景から起動 | 画面が応答し、作業対象が正しい |
| 登録と同一フォルダーの再登録 | 一覧へ表示され、再登録で重複を作らない |
| パックの親フォルダーを登録 | 配下の対象を取りこぼさず、結果を表示する |
| 更新・削除 | 意図した対象だけが変わり、GitHubと一覧へ反映される |
| Codex／Claudeへ依頼を渡す | 選択先の新規タスクに依頼、固定commit URL、検証値が届く |
| 無効フォルダー・通信失敗 | 原因と操作可能な復旧方法が表示され、修正後に再試行できる |
| 連続投入・処理中終了・再起動 | 応答を維持し、既存状態を保って再開できる |
| 公開途中の停止と再開 | 同じ処理を照合して続行し、重複PRやデータ損失がない |

合格記録は候補commit、配布物SHA-256、導入版、各操作の結果とログ参照で足りる。ユーザーの実スキル構成も登録試験に含める。公開操作を伴う試験は専用の試験保管庫を使用する。

## 9. 完了の言い方

上記が揃った場合だけ「Windows版MVPを公開済み」とする。macOSを含む全製品完成、AIの依頼成果の完成とは言わない。

最終報告は、公開版／PR、使い始める操作、受入結果、対象外の範囲の4点に絞る。未確認の機能を完成扱いにしない。

## 10. この方針で最短にする理由

ユーザーが求めた登録・利用・復旧を残し、並行開発と検証基盤の拡張を止める。既存の起動経路を1件ずつ直し、実操作で判断する。所要時間は未確定の起動原因に依存するため、根拠のない終了時刻は約束しない。
